真正的问题：当答案错了，你能指出证据究竟是在解析、切块、召回、重排、判断、上下文选择，还是生成阶段丢失的吗？

先别想模型。
先想一座图书馆。

RAG 的本质是把“找资料”和“写答案”分开。Agentic RAG 再增加一个证据审查员：他会看第一轮资料够不够，并决定回答、追查、澄清或停下。

原件与解析

新书入库后先拆包、编目。PDF/DOCX/TXT 被抽成带页码、章节和字符位置的文本。

切块与索引

长书被做成段落卡片；一份按语义坐标找，一份按关键词找，而且都保留回原文的路。

混合检索

语义检索与 BM25 各给一份候选；RRF 合并名次，再由 reranker 复核相关性。

证据门

审查首名相关度、问题覆盖和多跳来源。证据弱时，不急着写答案，而是换问法再找。

有依据的生成

DeepSeek 只拿到 Gate 审核过的最终证据集：单跳最多 4 个，多跳最多 6 个；它负责组织语言，不负责凭参数记忆发明事实。

引用与轨迹

答案带来源凭条；系统日志记录每一轮候选、决策、筛选、模型、耗时和降级。

一句话：模型是报告撰写员，不是藏书本身；Agent 是有预算的调查流程，不是无限自主循环。

Docker 不是接口。
它是可重复运行的外壳。

FastAPI 负责“接请求”；Docker 负责“把接请求的程序连同依赖稳定运行”；REST 负责“调用者按什么格式讲话”。点选三个运行边界查看里面有什么。

Docker

镜像、容器、依赖、启动命令、健康检查、端口和 volume。它不定义 `/v1/query` 的业务逻辑。

FastAPI

在 `api` 容器里运行的 Python Web 应用。它校验请求并把 `/v1/query` 交给 AgentService。

REST / MCP

REST 是现有稳定边界；未来 MCP 把工具映射到同一核心，不需要复制一套检索算法。

Trace 不是日志堆积。
它是一条因果链。

当用户说“原文明明有，为什么没答出来”，系统需要逐层回答：它有没有被解析、切成了什么、被哪路召回、为什么被压低、是否进入提示词。

query_received问题、知识库、不可变索引版本、轮次预算
retrieval_rounddense / sparse / RRF / rerank 候选、分数、耗时、重试
evidence_gateanswer / retry / clarify、原因、置信度、决策方法
query_plan第二轮子查询、规划方式与模型降级
context_selection进入模型和被丢弃的 chunk、绝对/相对门槛
answer_generation模型、选中证据、token、引用标记、是否降级
run_completed / stop最终 route、轮次、引用、耗时或预算终止原因
诊断顺序

先找证据在哪一步消失

不要一看到错误答案就立刻换模型。按信息损失顺序向下检查：

  1. 解析产物里有原文吗？
  2. chunk 是否完整包住依据？
  3. dense 或 BM25 召回了吗？
  4. RRF / reranker 是否压掉了？
  5. Evidence Gate 是否误拒？
  6. 上下文是否真的送给 DeepSeek？
  7. 生成是否忽略或曲解证据？

四个容易混淆的地方

点开查看。把这些边界分清，后面扩展 MCP、反馈闭环和自调优时就不容易把协议、应用、模型和学习机制混在一起。

Docker 就像 FastAPI，会生成接口？

不会。接口由 FastAPI 代码定义；Docker 只是运行 FastAPI 的标准环境，并把宿主端口 8080 映射到容器端口 8080。

简单问题可以让 DeepSeek 直接回答？

只有问候/产品帮助走规则直答。知识库事实问题全部先检索；所谓简单路径是一轮 hybrid RAG，不是模型凭参数记忆回答。

Agentic 等于自动自我调优？

不是。v0.1 的 Agentic 是在线执行状态机：观察证据并选择下一步。自动实验、反馈归因、发布门禁和自调优属于下一阶段 Harness Engineering。

所有模型都打包进应用 Docker？

不是。应用容器只有 Python 程序。Embedding 和 reranker 在 Mac 的 Model Runner 上利用 Metal；DeepSeek V4 Flash 在官方云端。
