2026-08-19 实现更新

本页保留“为什么要改”的决策快照；其中 Exact-only 与 structure_v1 已升级为可选择 Exact/HNSW 和 structure-first semantic fallback。当前实现、真实模型 smoke 与新取舍见 《自适应 Chunk 与可选择 Dense Search 升级报告》。

结论：架构方向正确，但首要短板已经不在 Agent。

“Gate 审核的证据 = DeepSeek 生成的证据 = 引用来源”已经闭环。下一步收益最高的工作，是文档范围与元数据、表格/扫描件解析、中文句界，以及可诊断的检索阶段损失；不是立刻引入 GraphRAG、自动调参或更自由的 Agent。

02 · SQLite & retrieval

“SQL 搜索”其实只做了一半

SQLite 负责存储和 FTS5/BM25 关键词召回；Dense 现在可按不可变索引版本选择缓存 Exact matrix 或持久化 USearch HNSW，Auto 默认小库 Exact、大库 HNSW。

SQLite FTS5 / BM25 · Top 20
Exact matrix / USearch HNSW · Top 20
RRF(k=60) · Top 12
Qwen reranker · Top 6

中文查询怎样进入 FTS5

项目没有直接依赖 unicode61 给中文分词，而是在入库和查询前自己生成词项：

混合检索 → 混 · 合 · 检 · 索 · 混合 · 合检 · 检索
最多 80 个词项 → 每项加引号 → 用 OR 连接

这样优先保证召回，但没有词性、停用词、实体、同义词和字段权重。中文单字会让“联合覆盖率”看起来比真实证据覆盖更乐观。

为什么 BM25 是升序

FTS5 把传统 BM25 结果乘以 -1，所以数值越小、排名越好；当前 ORDER BY bm25_score ASC 是正确的，不是方向写反。

RRF(chunk) = Σ 1 / (60 + rank)
只看两路名次，不直接混合余弦分数与 BM25 分数

RRF 是稳健 baseline，因为两类分数没有统一量纲。最终相关性仍由 reranker 重估。

实现事实现在的好处边界 / 风险判断
Dense 可选缓存 Exact matrix 或持久化 HNSWExact 保留完整召回 oracle；HNSW 提供规模路径HNSW 必须对 Exact 测 Recall@K；Auto 阈值需按真实 P95/内存校准已实现
FTS 的 text 同时含文件名、章节、页码和正文无需 LLM 就能给 chunk 增加一点局部语境BM25 无法对标题/章节/正文分别加权，通用文件名可能制造噪声建议拆字段
index_version_id 在 FTS5 中是 UNINDEXED结果仍会按不可变版本过滤历史版本很多时可能扩大 FTS 扫描范围；需要用多版本压测确认先压测
SQL 使用 bm25() 排序语义明确、结果正确SQLite 官方说明 ORDER BY rank 在带 LIMIT 时可能更快小优化
所有查询词用 OR召回友好，少因一个词缺失而漏检长问题容易用泛词召回；产品号、法规号等缺少精确通道加精确项加权
最重要的判断： 现在仍不需要为了“主流”就强制换向量数据库。系统已提供本地 HNSW，但 2 万向量实测仍是缓存 Exact 更快，因此 Auto 保守地在 10 万 chunk 后才切换。真正门槛应由领域 Recall@K、P95、内存和并发决定。

03 · Chunking

结构优先、字符预算、确定性上下文

当前 adaptive_v2 先尊重章节/页：有意义标题走结构句界，长通用 TXT/PDF section 复用本地 embedding 找语义断点；目标约 1100、最大 1600、重叠约 160 字符。

Chunk 01 · 0—1100Document + Section + Page
正文约 1100 字符
Chunk 02 · ≈940—2040尽量在句末/空行结束
保留前块尾部语境
Chunk 03 · ≈1880—2980永远不跨 section
位置写入 source metadata
≈160≈160

注意：这里是字符数，不是 token 数。中文 1100 字符和英文 1100 字符对模型上下文的成本不同。

文档先怎样变成 section

Markdown# 到 ###### 标题分节结构较好
DOCX按 Heading 段落样式分节表格未解析
PDFPyPDF 每页一个 section无 OCR / 版面理解
TXT整篇一个 section，再按字符切无显式结构

每块附带什么“上下文”

Document: policy.docx
Section: 退款条件
Page: 4

＋ 原始 chunk 正文

这段确定性元数据会进入 embedding、BM25 和 rerank。它可审计、零额外 API 成本；但不等同于为每块生成“该块在整篇文档中的含义摘要”。

已修：中文句界不再要求标点后有空白

。！？ 可以直接形成边界；英文句点只在空白或结尾前切分，避免把 3.14 当成两句。结构与语义路径都有回归测试。

P0：表格与扫描件是“原文存在，但检索永远找不到”的典型根因

DOCX 表格未进入 section，扫描 PDF 没有 OCR。此时 reranker、Gate、查询改写都无法修复，因为证据从未进入索引。失败归因必须先区分 parse miss，再谈 retrieval miss。

已实现：语义边界检测；仍不默认生成 chunk 摘要

Auto 对弱结构长段使用现有本地 embedding 做相邻句窗差异，不改写原文。生成式 Contextual Retrieval 仍是独立候选，因为摘要会增加成本、隐私面和证据污染风险。

P1：parent-child / sentence-window 值得怎样试

用小块提高召回；命中后再扩展父章节或邻句，把“扩展后的最终证据”统一交给 Gate。LlamaIndex 的 AutoMergingRetriever 就体现了“小节点命中、邻居补齐、满足条件后合并父节点”的思路。必须记录扩展前后 chunk ID 与 token 增量。

04 · Mainstream map

借它们的约束，不照搬它们的复杂度

GitHub 热度只能证明使用广，不证明适合本项目。这里关注的是官方实现反复出现的工程共识，以及它们恰好怎样映射到你的失稳样例。

LangGraphAgent state

显式状态、可恢复执行、HITL；Self-RAG 路线是 retrieve → grade → rewrite → generate。

我们借： 有预算的状态机和 trace。
不借： 无限循环和每步都 LLM 化。

RAGFlowEvidence substrate

强调深文档解析、混合召回、rerank、元数据过滤和 document scope；这正是当前项目的最大缺口。

我们借： 范围过滤、字段权重、结构化解析。
不借： v0.1 就复制完整平台。

LlamaIndexRetrieval patterns

Auto-merging、邻居补齐和多种 fusion 模式，适合作为可归因的离线实验。

我们借： parent-child 候选实验。
不借： 未经数据验证的默认复杂管线。

HaystackModularity

检索器、路由器、生成器和 Agent 状态均是可替换组件，契合“应用本体 + 可调用服务”的方向。

我们借： 清晰契约与 provider adapter。
不借： 为抽象而抽象。

RAGCheckerDiagnostics

把检索 claim recall/context precision 和生成 context utilization/noise sensitivity 分开，避免只看一个总分。

我们借： 阶段级、claim 级失败归因。
不借： 只为了分数堆评测器。

Microsoft 架构指南Service boundary

建议先把优化过的 hybrid/rerank/filter 管线封装成工具，并返回标题、日期、文档 ID、相关性分数。

我们借： REST 核心服务 + 后续 MCP 适配。
不借： 把事实判断交给相关性分数。

共同信号： 成熟实现并不是“多调用几次大模型”，而是把 parser、metadata filter、hybrid retrieval、rerank、状态、评测拆开，使每个阶段可替换、可测、可归因。你现在的 EvidenceSet 不变量已经走在正确方向；下一个地基是 document scope 与 evidence semantics。

05 · Decision queue

按“现在 / 实验 / 以后”排队

按钮不是路线图装饰，而是在区分三类动作：可由已有失败直接证明、需要 A/B 验证、以及尚未达到触发条件。

06 · Existing evidence

改 Gate 后没有性能塌陷，但也没有治好上游

Failure Lab 新旧结果说明 EvidenceSet 改造是行为一致性修复，不是质量魔法。真正失败仍集中在文档范围、解析、冲突和提示注入。

QASPER 真实例子说明了什么

“他们实验了哪些数据集？”在包含 5 篇论文的知识库中没有文档范围。系统跨论文找到 MultiUN，却漏 Europarl，并混入其他论文的数据集。根因更接近 scope/metadata ambiguity，不是“多跳 Top 6 还不够”。

下一版失败标签应该怎样走

parse miss→chunk miss→recall miss→fusion loss→rerank loss→gate error→generation error

只有先知道 gold evidence 在哪一层消失，后续 self-tuning 才不会错误调参。

不要把相关性当可信度： rerank rank/score 可以作为 DeepSeek 的相关性提示，但无法证明来源权威、版本最新、文本没有提示注入，也无法解决两个来源彼此冲突。

07 · Hooks

四个需要未来数据回答的问题

这些不是现在应擅自定死的参数。它们会真正改变产品契约或成本，应成为下一阶段的实验输入。

“引用”究竟表示什么？

当前 API 为保持不变量，返回整个审核证据集。未来是否拆成 evidence_sources（Gate 全集）与 claim_citations（回答实际使用的子集）？

本地知识库的规模上限是多少？

要到 1 万、10 万还是 100 万 chunk？先以 P95 延迟和内存压测定义 ANN 迁移门槛，而不是凭框架潮流换库。

领域元数据最小公约数是什么？

通用产品至少可提供标题、文档类型、标签、发布日期、有效期、权威等级；但法律、医疗、工程各自还需要什么字段？

愿意为离线上下文付多少成本？

Anthropic 式 chunk context 可能提高召回，也可能增加 API 成本、泄露面和生成噪声。应按领域、语言、chunk 配置做离线 A/B，而非默认开启。

这份报告刻意没有展开的内容

Docker、REST、Web UI、MCP 基础概念，以及传统 RAG 定义。它们仍在原有心智模型报告中；但对当前 v0.1 质量决策的边际价值较低。本报告把篇幅留给了 SQL、chunk、证据边界和具体失稳点。
